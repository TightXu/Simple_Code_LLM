# Design Notes — Code LLM 435M

**A clean 31B-token baseline and a controlled ablation framework for small code models.**

> This document records the design decisions and the evidence behind them: what was built, which decisions were made at each step, and why. The rationale columns are the point of the tables.
>
> Elsewhere in this repo: the narrative overview is in [`README.md`](README.md), the bug stories are in [`CHALLENGES.md`](CHALLENGES.md), and the supervised fine-tuning experiments on top of this baseline are in [`post-training/POST_TRAINING.md`](post-training/POST_TRAINING.md).

---

## 1. Introduction

I trained a 434.7M-parameter decoder-only Transformer on 31B tokens of rigorously filtered Python code, and use it as a controlled baseline for ablation studies: which factor determines quality at this size — data quality, data scale, tokenizer, or context length.

It is the second version of a from-scratch code-LLM project that started with a 353M model (archived in `archive/353M/`). That first model succeeded (it learned to generate recursive Fibonacci at ~8B tokens) but carried three known defects: loose data filtering, about 8B tokens inadvertently trained twice because resume restarted the dataset from the top, and a mid-training learning-rate increase without resetting the optimizer. An intermediate attempt at this model, "435M v1", then failed outright across 21.5B tokens, and every design decision in this report answers something it exposed; the failure itself is summarized once, in [`CHALLENGES.md`](CHALLENGES.md).

**Headline result**: at similar parameter count, the clean baseline scores **66/100** on a 10-task human-graded code-generation benchmark vs **6/100** for the first model, and continuing to train the first model on repeated data *degraded* it further (4/100), which directly shows what the resume bug cost.

## 2. Dataset

Three public sources, filtered and merged into one continuous 31.01B-token stream:

| Dataset | Tokens | Role | Rationale |
|---|---|---|---|
| codeparrot_clean | 4.13B | First | Same distribution as the tokenizer training sample — the model's "first language" matches its vocabulary |
| the_stack_v1 (Python) | 18.51B | Second | Bulk and diversity; permissively licensed |
| star_coder_data (Python) | 8.37B | Third | Different provenance; metadata already stripped |

**Filtering pipeline** (each layer addresses a failure found in the earlier attempts):

| Layer | Removes | Rationale |
|---|---|---|
| Language | non-`.py` | the earlier multilingual tokenizer wasted capacity on Java/JS/HTML tokens |
| L1 | framework templates (Django migrations, Flask routes, Plotly validators) | exact-match; these poisoned the 353M's fine-tuning experiments |
| L2 | Python 2 relics (`__future__`, `xrange`, coding headers) | wrong dialect |
| L3 | config/license/setup files | not learnable code |
| L4 | test files | test boilerplate dominates simple filters |
| L5 | quality thresholds (import ratio, class ratio, repetition rate, empty bodies) | statistical junk |
| L6 | autogenerated patterns (UUIDs, numeric spam, template vars) | non-semantic content |
| Copyright | license headers (second pass) | first pass left residue |
| Metadata | `<gh_stars>` / `<filename>` / `<reponame>` prefixes | **20% of star_coder samples** carried these; the earlier pipeline never stripped them |

**Key decision: one merged stream.** I concatenate the three tokenized datasets into a single 62GB `train.bin` and train it as one continuous run (a single 630,979-step LR schedule, computed once). No dataset boundaries, no optimizer resets mid-flight. The 353M first version's training loop, and the abandoned 435M attempt that followed it, both did sequential multi-dataset rounds with an `--auto-resume` flag, and that design is what caused the repeat-training bug described in the introduction. Concatenating into one stream makes that whole class of failure structurally impossible instead of merely avoided.

## 3. Tokenization

| Property | Value | Rationale |
|---|---|---|
| Algorithm | Byte-level BPE | same as GPT-2; proven for code |
| Vocabulary | 32,000 | fits 1024-dim embedding budget |
| Training data | uniform sample across **all three filtered datasets** (shuffled, 80K rows each) | a tokenizer trained on "the first few files" of one source mismatches the rest; distribution match is the whole point |
| Compression | 3.64 chars/token | +2.6% over the earlier generic BPE (3.54); vocabulary contains `pandas`/`asyncio`/`flask` instead of `ArrayList`/`webpack`/`php` |
| Special tokens | `<pad>`, `<eos>`, `<unk>` | — |

This tokenizer replaced the multilingual BPE inherited from the 353M generation and used again by the failed 435M v1: only 65.7% of the two vocabularies overlap, **20,851 shared token IDs map to different strings**, and it had no `<gh_stars>` token while 20% of training samples began with that literal prefix (what that mismatch cost is in [`CHALLENGES.md`](CHALLENGES.md)). Retraining on a uniform sample of the actual filtered corpus is the cleanest illustration of "distribution match matters".

## 4. Model architecture

```
Input Tokens (seq_len=1024)
        │
        ▼
  Token Embedding (32K → 1024)
        │
        ▼
  ┌─────────────────────────┐
  │ Transformer Block × 22   │
  │  ┌─────────────────────┐ │
  │  │ RMSNorm → Attention │ │
  │  │    (RoPE, 16 heads) │─┼── + Residual
  │  │ RMSNorm → SwiGLU FFN│ │
  │  │    (1024 → 4096)    │─┼── + Residual
  │  └─────────────────────┘ │
  └─────────────────────────┘
        │
        ▼
  Final RMSNorm
        │
        ▼
  LM Head (1024 → 32K, untied)
```

| Parameter | Value | Rationale |
|-----------|-------|-----------|
| Parameters | 434.7M | deepest/widest that sustains 52K tok/s at batch 11 on 32GB with compile |
| Layers | 22 | deeper than the 353M model's 18 (this architecture carried over from the failed 435M v1 unchanged; the architecture was never the problem) |
| `d_model` | 1024 | standard for this scale |
| Attention heads | 16 | `d_model / 64` |
| `d_ff` (SwiGLU) | 4096 | 4.0× expansion |
| Vocabulary | 32,000 | matched pure-Python BPE |
| Context length | 1024 | ablation variable (see §8) |
| Position / Norm / Activation | RoPE / RMSNorm / SwiGLU | identical choices to 353M, kept constant so data factors are the only variables |

Parameter count is intentionally *not* the experiment: 353M (18L/3840) and 435M (22L/4096) differ, which is why the cross-model comparison (§7.2) is corroborating evidence, not the controlled result. All controlled claims come from the ablation framework (§8), which fixes the 435M architecture.

## 5. Loss function

Standard next-token cross-entropy over the 32K vocabulary:

$$\mathcal{L} = -\frac{1}{N} \sum_{i=1}^{N} \log P(y_i \mid x_{<i})$$

No padding-masking subtleties: offline `.bin` packing produces only full 1024-token sequences, so every position is a real training signal.

Perplexity at final val loss 1.2363 ≈ **3.44**: the model's average per-position uncertainty is down to ~3.5 candidate tokens, vs ≈ 7.2 for the failed v1 (1.97).

## 6. Training configuration

| Parameter | Value | Rationale |
|-----------|-------|-----------|
| Optimizer | AdamW (β₁=0.9, β₂=0.95, wd=0.1) | LLM standard |
| Peak LR | 2.5e-4 | stable-phase constant (WSM) |
| Schedule | **WSM**: linear warmup 500 steps → constant 2.5e-4 → final 30K steps cooldown to 1e-4 | constant-LR phase gives clean checkpoints for weight averaging; the cooldown recovers tail quality without a full cosine cycle |
| Batch | BS 11 → 12 (changed mid-run), 4 accum: 44 seqs @ 1024 = 45,056 tok/step, then 48 seqs = 49,152 tok/step | largest that fits with compile on 24GB-class headroom |
| Precision | BF16 mixed | — |
| torch.compile | **`default` mode** | `reduce-overhead` (CUDA graphs) measured *20% slower* on sm_120 + PyTorch 2.13 (52K vs 43K tok/s), plus CUDAGraph static-buffer errors; see CHALLENGES.md |
| Checkpoints | every 5,000 steps + tail every 500 | enables both scaling-law snapshots and merge-window selection |
| Merge | weighted average of last 10K steps (cooldown segment 30% / stable segment 70% weight, by LR) | treats the cooldown as a distinct quality regime rather than averaging it away |

**Checkpoint hygiene** (each of these cost me a run; see [`CHALLENGES.md`](CHALLENGES.md)): optimizer created *after* resume; `torch.compile` re-applied after resume; `_orig_mod.` prefix stripped on save/load; scheduler reads `initial_lr` not current LR (the active_lr bug that silently killed the first cooldown attempt); `.bin` reads use explicit `encoding="utf-8"` (Windows GBK default crashed a training run at 31%).

## 7. Results

### 7.1 Training

| Metric | Value |
|--------|-------|
| Final step | 639,061 (30.98B tokens, 99.9% of the 31.01B stream) |
| Throughput | 52K tok/s, ~164h on one RTX 5090 |
| Val loss (merged checkpoint) | **1.2363** |
| Best val loss in the training log | 1.2416 (step 625,000) |
| Train loss | ~1.34 |

For reference: failed v1 stuck at val 1.97 (never lower); 353M ended at 1.21 on 16.09B cumulative (10.6B unique) tokens.

How these two numbers were measured. The merged model is an average of the last 10K checkpoints (weighted merge, §6), not the last training checkpoint; it is evaluated on the same held-out shard the log evals use (`data/all/val.bin`, 1024-token sequences, a fixed 200-batch sample), which is what makes the row directly comparable to the log. The log row is the minimum of the logged val series. The final checkpoint also carries a `best_val_loss` field of 1.2191, a run-level running minimum that does not match the log (a known behaviour of that field), so the log value is the one used here — same rule as in [`ablation/ABLATION_REPORT.md`](ablation/ABLATION_REPORT.md).

### 7.2 Cross-model human evaluation (353M vs 435M)

10 algorithm tasks × 5 seeds, each generation graded 0/1/2 by human review (0 = wrong/noise, 1 = right idea wrong details, 2 = fully correct). Max 100. Script-based pass rates were computed but demoted to auxiliary evidence, because they proved unreliable in both directions (see §8.3).

| Model | fib | quicksort | binary_search | two_sum | mergesort | **Total (10 tasks)** |
|---|---|---|---|---|---|---|
| 353M @8B | 5 | 1 | 0 | 0 | 0 | **6/100** |
| 353M @16B (continued on repeated data) | 3 | 0 | 1 | 0 | 0 | **4/100** |
| **435M @31B** | 7 | 8 | 8 | 8 | 9 | **66/100** |

Qualitative signature of the gap: the 353M models produce comments, docstrings, or unrelated code where 435M produces working implementations. The 353M@16B regression is the resume bug paying dividends: on the archive's 14-seed human review of both checkpoints, recursive structure on fibonacci fell from 14/14 to 7/14 after the second pass, which was pure repetition (see [`archive/353M/README.md`](archive/353M/README.md)).

### 7.3 Emergence of recursion (scaling snapshot)

Fibonacci generations showing recursive structure (`n-1`/`n-2` self-calls), 5 seeds per checkpoint:

| Tokens | 1B | 2B | 5B | 10B | 20B | 31B (merged) |
|---|---|---|---|---|---|---|
| Recursive structure | 0/5 | 0/5 | 0/5 | 2/5 | 2/5 | **5/5** |

Consistent with the 353M finding (breakthrough between 2.6B and 7.7B on a weaker data diet): recursion is a late, qualitative acquisition, and it is data-scale-dependent.

---

### 7.4 Post-training (supervised fine-tuning)

About 30 SFT runs on the merged baseline, evaluated on 11 tasks × 20 attempts per prompt style with hand-audited raw outputs.

The only lever that reliably helped was training on **verified** instruction data (the "gold standard" corpus: instruction examples whose reference solution passes its unit tests). It lifted the natural-language column from 42% (small public-instruction mix, 5-attempt protocol) to 78% with gold data alone, and to 91% at 20-attempt precision. The signature column fell as the gold share rose, and the combined score stayed in the 65–75% band across every gold:signature ratio from 1:1 to 8:1. These are pass rates out of attempts, a different measure from the 0/1/2-graded benchmark in §7.2 and not comparable to it.

Random-seed variance (±6 points) was larger than any recipe difference, weight averaging never beat its best parent model, and the leader on the tuning set finished **last** on 12 unseen tasks. The shipped model is the one that validated on the held-out set. Full experiment log, corrections included: [`post-training/POST_TRAINING.md`](post-training/POST_TRAINING.md).

## 8. Ablation framework

All experiments train the **same 435M architecture from scratch**, with the same tokenizer, batch, LR schedule and val set. One variable at a time.

### 8.1 Design

| # | Experiment | Groups | Target tokens |
|---|-----------|--------|---------------|
| 1 | Data scaling | 1B / 2B / 5B / 10B / 20B / 31B | as named |
| 2 | Data quality | strict filter vs no-filter (language-only) | 1B pilot → 18B full |
| 3 | Tokenizer | generic BPE vs code-optimized BPE | matched char budget |
| 4 | Context length | 512 / 1024 / 2048 | 50M each |
| 5 | LR schedule | WSM vs Cosine | matched |

### 8.2 Results so far

| Experiment | Result | Status |
|-----------|--------|--------|
| Data quality @1B | no-filter val 1.91 vs filtered 1.71 → filtering is worth ~0.2 val loss at 1B tokens | done |
| Data quality @18B | 18.004B vs 18.002B tokens: filtered val 1.4103 vs no-filter 1.4315 at the mark, −0.118 mean over 73 token-aligned points, both 0/50 on the five-algorithm suite, HumanEval 4/1,630 vs 0/1,630 | done ([`ablation/ABLATION_REPORT.md`](ablation/ABLATION_REPORT.md)) |
| Scaling (recursion emergence) | §7.3 above | first pass |
| Tokenizer | closed by design, not run: 32K→64K vocabulary buys +1.6–2.8% compression for +7.5–15.1% parameters | closed |
| Context length | closed by design, not run: 50M tokens per arm is far below the scale at which this model separates | closed |
| LR schedule (WSM vs cosine) | not run | open |

### 8.3 Evaluation methodology (a result in itself)

Five evaluation failures were diagnosed and fixed over the course of this project, and they generalize:

1. **Script pass-rates cheat**: a test asserting output correctness is passed by `return arr.sort()`, so the model "solved" quicksort with a builtin. Fix: implementation checks (does binary search actually contain a `mid`? is `sort()` banned?) plus human grading.
2. **Script pass-rates false-negative**: logically correct solutions failed on tab/space mixing (TabError). Fix: human review as the primary metric, scripts as secondary.
3. **Base models don't read docstrings**: a from-scratch (non-instruction-tuned) model treats a docstring as the end of the function and continues with comments/test code — standard HumanEval prompts pass no problem on any checkpoint (0/164 problems). Fix: docstring-free prompts (`def fibonacci(n):` + trailing indent), which is also how the 353M numbers were obtained. HumanEval is kept in the harness for completeness with this caveat.
4. **Batch generation OOMs**: per-sample generation (≈1GB peak) vs batched attention-mask generation (5× estimated peak, SDPA inefficiency).
5. **Reference-pass false negatives for docstring-writers** (found 2026-09-10): even with docstring-free *prompts*, a model trained on GitHub-style code writes a docstring first (`"""Binary search..."""`), consumes the generation budget, and leaves the function body truncated. Judging the raw continuation text → 0% pass on logically-correct implementations.

   Fix: `extract_function_body(prompt + gen)` finds the first `def `, keeps the function body, and truncates at the first top-level line (garbage like `# Driver Code` / `import numpy...`). Only that core is judged. Verdict: 0/50 → 7/50 on v2 (fibonacci 3/10, binary_search 3/10, two_sum 1/10; quicksort and mergesort stayed 0 because the model genuinely lacks merge/partition helpers, so strictness holds). No false positives: AST-unparseable samples still fail, and no empty-body sample passes.

   The lesson generalizes: the judging has to be compatible with the model distribution, not just the prompt style.

## 9. Discussion

### Data quality is a multiplier, not an additive term

The same 435M architecture produced no usable generation at all when fed v1's mismatched pipeline (training-log val 1.97) and scores 66/100 when fed the clean pipeline (training-log val 1.27 at the 31B mark; the merged checkpoint measures 1.2363, §7.1). Nothing about the model changed. The v1→v2 delta decomposes into: **a resume path that actually works** (v1's optimizer-references-dead-model bug froze training; its val 1.97 is that bug, not a data-law failure), a matched tokenizer, metadata stripping, data order, and zero repetition. Each is individually small, and jointly they are decisive.

353M's still-decent generation with its own loose tokenizer shows that the tokenizer mismatch was a supporting factor rather than the primary culprit. The frozen-training bug is the primary one.

### Loss orders models but does not measure them

val loss ordered every model correctly (1.97 → 1.27 → 1.21), but within-model claims such as "is 16B better than 8B?" were invisible or *inverted* in loss (0.91 best vs 1.21 final) while human review showed an unambiguous regression. The three loss numbers are not measured the same way: 1.97 and 1.27 are training-log val for the two 435M attempts at the 31B mark, 1.21 is the 353M's final under a cosine schedule, and the 435M's merged checkpoint measures 1.2363 (§7.1). For small models, loss is a coarse instrument.

### The v1 failure produced the v2 design

Every design decision in this report maps to a specific v1 failure, and the v1 post-mortem (optimizer/object-identity bug as the primary culprit, tokenizer mismatch, cumulative-token arithmetic) caught bugs that would otherwise have silently corrupted v2 as well: the active_lr cooldown bug in v2 was found *because* the v1 audit taught me to diff expected vs actual LR trajectories.

## 10. Future work

1. **The no-filter run at 31B.** The 18B comparison is done and reported in [`ablation/ABLATION_REPORT.md`](ablation/ABLATION_REPORT.md): filtering wins, but the val-loss gap narrows from −0.13/−0.14 mid-training to −0.067 in the last window and −0.021 at the 18B mark. Whether it closes or inverts once the no-filter arm sees 31B unique tokens is still open.
2. **Tokenizer and context-length ablations.** Closed by design at this scale rather than skipped (see [`ablation/README.md`](ablation/README.md)); worth revisiting only with a budget of tens of billions of tokens per arm.
3. **Schedule ablation** (WSM+merge vs full cosine), not run.
4. **Fine-tuning on the clean baseline**: done (about 30 runs; see [`post-training/POST_TRAINING.md`](post-training/POST_TRAINING.md)). The open question is the one that report ends on: whether execution-feedback preference learning beats further data/recipe tuning.
5. **Public release**: checkpoints to HuggingFace Hub, this repo with complete ablation tables

## 11. What I learned

- **Silent bugs are the expensive ones.** The optimizer-referencing-a-dead-model bug ran for days, producing healthy-looking logs and no learning. Every resume path now gets an object-identity audit.
- **Distribution match is the deepest recurring theme**: tokenizer↔data, fine-tune-data↔eval-task, filter-rule↔corpus. Three different bugs, one principle.
- **Windows is a real training platform, with real footguns**: commit-memory OOM masquerading as VRAM OOM, GBK default encodings, CUDA-graph slowdowns on sm_120. All documented in CHALLENGES.md.
- **Evaluation is a research problem**: the project had to build, and then partially dismantle, an execution-based harness before concluding that human-graded generation with fixed prompts is the honest metric at this scale.
- **Write the post-mortem while it hurts.** The v1 failure log is the reason v2 could be trained once, cleanly, in one pass.
