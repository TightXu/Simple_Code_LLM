# Code LLM 435M — Technical Report

**A Clean 31B-Token Baseline and a Controlled Ablation Framework for Small Code Models**

---

## 1. Introduction

This project trains a 434.7M-parameter decoder-only Transformer on 31B tokens of rigorously filtered Python code, then uses the result as a controlled baseline for ablation studies: *which factor — data quality, data scale, tokenizer, or context length — actually moves the needle for a small code model?*

It is the second version of a from-scratch code-LLM project that started with a 353M model (archived in `archive/353M/`). That first model succeeded — it learned to generate recursive Fibonacci at ~8B tokens — but carried three known defects: loose data filtering, about 8B tokens inadvertently trained twice because resume restarted the dataset from the top, and a mid-training learning-rate increase without resetting the optimizer. An intermediate attempt in this project, "435M v1", failed completely: val loss stuck at 1.97 and generation collapsed. Its failure analysis is the reason the design decisions in this report exist.

**Headline result**: at similar parameter count, the clean baseline scores **66/100** on a 10-task human-graded code-generation benchmark vs **6/100** for the first model — and continuing to train the first model on repeated data *degraded* it further (4/100), which directly shows what the resume bug cost.

## 2. Dataset

Three public sources, filtered and merged into one continuous 31.01B-token stream:

| Dataset | Tokens | Role | Rationale |
|---|---|---|---|
| codeparrot_clean | 4.13B | First | Same distribution as the tokenizer training sample — the model's "first language" matches its vocabulary |
| the_stack_v1 (Python) | 18.51B | Second | Bulk and diversity; permissively licensed |
| star_coder_data (Python) | 8.37B | Third | Different provenance; metadata already stripped |

**Filtering pipeline** (each layer addresses a v1 failure):

| Layer | Removes | Rationale |
|---|---|---|
| Language | non-`.py` | v1's tokenizer wasted capacity on Java/JS/HTML tokens |
| L1 | framework templates (Django migrations, Flask routes, Plotly validators) | exact-match; these poisoned v1's fine-tuning experiments |
| L2 | Python 2 relics (`__future__`, `xrange`, coding headers) | wrong dialect |
| L3 | config/license/setup files | not learnable code |
| L4 | test files | test boilerplate dominates simple filters |
| L5 | quality thresholds (import ratio, class ratio, repetition rate, empty bodies) | statistical junk |
| L6 | autogenerated patterns (UUIDs, numeric spam, template vars) | non-semantic content |
| Copyright | license headers (second pass) | first pass left residue |
| Metadata | `<gh_stars>` / `<filename>` / `<reponame>` prefixes | **20% of star_coder samples** carried these; v1 never stripped them |

**Key decision — one merged stream**: the three tokenized datasets are concatenated into a single 62GB `train.bin` and trained as one continuous run (688K-step LR schedule computed once). No dataset boundaries, no optimizer resets mid-flight. The first version's training loop (and the failed "435M v1" attempt) did sequential multi-dataset rounds with an `--auto-resume` flag, and that design is what caused the repeat-training bug described in the introduction. Concatenating into one stream makes that whole class of failure structurally impossible instead of merely avoided.

## 3. Tokenization

| Property | Value | Rationale |
|---|---|---|
| Algorithm | Byte-level BPE | same as GPT-2; proven for code |
| Vocabulary | 32,000 | fits 1024-dim embedding budget |
| Training data | uniform sample across **all three filtered datasets** (shuffled, 80K rows each) | v1 lesson: a tokenizer trained on "the first few files" of one source mismatches the rest; distribution match is the whole point |
| Compression | 3.64 chars/token | +2.6% over v1's generic BPE (3.54); vocabulary contains `pandas`/`asyncio`/`flask` instead of `ArrayList`/`webpack`/`php` |
| Special tokens | `<pad>`, `<eos>`, `<unk>` | — |

The tokenizer before this project (used by both the first model and the failed "435M v1") was a multilingual BPE: 65.7% of its vocabulary overlapped with the current one, but **20,851 shared token IDs mapped to different strings**, and it was trained on multilingual code while the training data was pure Python. It also lacked a `<gh_stars>` token while 20% of training samples began with that literal string. Retraining the tokenizer on a uniform sample of the actual filtered corpus is the cleanest illustration of "distribution match matters".

## 4. Model Architecture

```
Input Tokens (seq_len=1024)
        │
        ▼
  Token Embedding (32K → 1024)
        │
        ▼
  ┌─────────────────────────┐
  │ Transformer Block × 22   │
  │  ┌─────────────────────┐ │
  │  │ RMSNorm → Attention │ │
  │  │    (RoPE, 16 heads) │─┼── + Residual
  │  │ RMSNorm → SwiGLU FFN│ │
  │  │    (1024 → 4096)    │─┼── + Residual
  │  └─────────────────────┘ │
  └─────────────────────────┘
        │
        ▼
  Final RMSNorm
        │
        ▼
  LM Head (1024 → 32K, untied)
```

| Parameter | Value | Rationale |
|-----------|-------|-----------|
| Parameters | 434.7M | deepest/widest that sustains 52K tok/s at batch 11 on 32GB with compile |
| Layers | 22 | deeper than v1's 18 (v1 arch carried over — the architecture was never the problem) |
| `d_model` | 1024 | standard for this scale |
| Attention heads | 16 | `d_model / 64` |
| `d_ff` (SwiGLU) | 4096 | 4.0× expansion |
| Vocabulary | 32,000 | matched pure-Python BPE |
| Context length | 1024 | ablation variable (see §8) |
| Position / Norm / Activation | RoPE / RMSNorm / SwiGLU | identical choices to 353M — kept constant so data factors are the only variables |

Parameter count is intentionally *not* the experiment: 353M (18L/3840) and 435M (22L/4096) differ, which is why the cross-model comparison (§7.2) is corroborating evidence, not the controlled result. All controlled claims come from the ablation framework (§8), which fixes the 435M architecture.

## 5. Loss Function

Standard next-token cross-entropy over the 32K vocabulary:

$$\mathcal{L} = -\frac{1}{N} \sum_{i=1}^{N} \log P(y_i \mid x_{<i})$$

No padding-masking subtleties: offline `.bin` packing produces only full 1024-token sequences, so every position is a real training signal.

Perplexity at final val loss 1.2363 ≈ **3.47** — the model's average per-position uncertainty is down to ~3.5 candidate tokens, vs ≈ 7.2 for the failed v1 (1.97).

## 6. Training Configuration

| Parameter | Value | Rationale |
|-----------|-------|-----------|
| Optimizer | AdamW (β₁=0.9, β₂=0.95, wd=0.1) | LLM standard |
| Peak LR | 2.5e-4 | stable-phase constant (WSM) |
| Schedule | **WSM**: linear warmup 500 steps → constant 2.5e-4 → final 30K steps cooldown to 1e-4 | constant-LR phase gives clean checkpoints for weight averaging; the cooldown recovers tail quality without a full cosine cycle |
| Batch | 11 × 4 accum = 44 seqs @ 1024 = 45,056 tok/step | largest that fits with compile on 24GB-class headroom |
| Precision | BF16 mixed | — |
| torch.compile | **`default` mode** | `reduce-overhead` (CUDA graphs) measured *20% slower* on sm_120 + PyTorch 2.13 (52K vs 43K tok/s), plus CUDAGraph static-buffer errors; see CHALLENGES.md |
| Checkpoints | every 5,000 steps + tail every 500 | enables both scaling-law snapshots and merge-window selection |
| Merge | weighted average of last 10K steps (cooldown segment 30% / stable segment 70% weight, by LR) | treats the cooldown as a distinct quality regime rather than averaging it away |

**Checkpoint hygiene** (all learned the hard way — see CHALLENGES.md): optimizer created *after* resume; `torch.compile` re-applied after resume; `_orig_mod.` prefix stripped on save/load; scheduler reads `initial_lr` not current LR (the active_lr bug that silently killed the first cooldown attempt); `.bin` reads use explicit `encoding="utf-8"` (Windows GBK default crashed a training run at 31%).

## 7. Results

### 7.1 Training

| Metric | Value |
|--------|-------|
| Final step | 639,061 (99.9% of 31.01B target) |
| Throughput | 52K tok/s, ~96h on one RTX 5090 |
| Val loss (merged checkpoint) | **1.2363** |
| Best val loss during training | 1.2191 (step 621,555) |
| Train loss | ~1.34 |

For reference: failed v1 stuck at val 1.97 (never lower); 353M ended at 1.21 on 16.09B cumulative (10.6B unique) tokens. The merged number is measured on the averaged checkpoints (weighted merge of the last 10K steps), not the last training checkpoint.

### 7.2 Cross-Model Human Evaluation (353M vs 435M)

10 algorithm tasks × 5 seeds, each generation graded 0/1/2 by human review (0 = wrong/noise, 1 = right idea wrong details, 2 = fully correct). Max 100. Script-based pass rates were computed but demoted to auxiliary evidence — they proven unreliable in both directions (see §8.3).

| Model | fib | quicksort | binary_search | two_sum | mergesort | **Total (10 tasks)** |
|---|---|---|---|---|---|---|
| 353M @8B | 5 | 1 | 0 | 0 | 0 | **6/100** |
| 353M @16B (continued on repeated data) | 3 | 0 | 1 | 0 | 0 | **4/100** |
| **435M @31B** | 7 | 8 | 8 | 8 | 9 | **66/100** |

Qualitative signature of the gap: the 353M models produce comments, docstrings, or unrelated code where 435M produces working implementations. The 353M@16B regression (fibonacci recursive structure fell from 14/14 seeds to 7/14 after "more training") is the resume-bug paying dividends: the second 8B pass was pure repetition.

### 7.3 Emergence of Recursion (scaling snapshot)

Fibonacci generations showing recursive structure (`n-1`/`n-2` self-calls), 5 seeds per checkpoint:

| Tokens | 1B | 2B | 5B | 10B | 20B | 31B (merged) |
|---|---|---|---|---|---|---|
| Recursive structure | 0/5 | 0/5 | 0/5 | 2/5 | 2/5 | **5/5** |

Consistent with the 353M finding (breakthrough between 2.6B and 7.7B on a weaker data diet): recursion is a late, qualitative acquisition, and it is data-scale-dependent.

## 8. Ablation Framework

All experiments train the **same 435M architecture from scratch** — same tokenizer, batch, LR schedule, val set. One variable at a time.

### 8.1 Design

| # | Experiment | Groups | Target tokens |
|---|-----------|--------|---------------|
| 1 | Data scaling | 1B / 2B / 5B / 10B / 20B / 31B | as named |
| 2 | Data quality | strict filter vs no-filter (language-only) | 1B pilot → 18B full |
| 3 | Tokenizer | generic BPE vs code-optimized BPE | matched char budget |
| 4 | Context length | 512 / 1024 / 2048 | 50M each |
| 5 | LR schedule | WSM vs Cosine | matched |

### 8.2 Results So Far

| Experiment | Result | Status |
|-----------|--------|--------|
| Data quality @1B | no-filter val 1.91 vs filtered 1.71 → **filtering is worth ~0.2 val loss at 1B tokens** | √ |
| Data quality @18B | in training; at every matched checkpoint so far (0.23B/0.90B/5.72B) no-filter trails by +0.10~0.23 val loss | in progress |
| Scaling (recursion emergence) | §7.3 above | √ first pass |
| Tokenizer / context / schedule | framework ready | planned |

### 8.3 Evaluation Methodology (a result in itself)

Three evaluation failures were diagnosed and fixed over the course of this project, and they generalize:

1. **Script pass-rates cheat**: a test asserting output correctness is passed by `return arr.sort()` — the model "solved" quicksort with a builtin. Fix: implementation checks (does binary search actually contain a `mid`? is `sort()` banned?) plus human grading.
2. **Script pass-rates false-negative**: logically correct solutions failed on tab/space mixing (TabError). Fix: human review as the primary metric, scripts as secondary.
3. **Base models don't read docstrings**: a from-scratch (non-instruction-tuned) model treats a docstring as the end of the function and continues with comments/test code — standard HumanEval prompts score 0/164 across *all* checkpoints. Fix: docstring-free prompts (`def fibonacci(n):` + trailing indent), which is also how the 353M numbers were obtained. HumanEval is kept in the harness for completeness with this caveat.
4. **Batch generation OOMs**: per-sample generation (≈1GB peak) vs batched attention-mask generation (5× estimated peak, SDPA inefficiency).
5. **Reference-pass false negatives for docstring-writers** (found 2026-09-10): even with docstring-free *prompts*, a model trained on GitHub-style code writes a docstring first (`"""Binary search..."""`), consumes the generation budget, and leaves the function body truncated. Judging the raw continuation text → 0% pass on logically-correct implementations. Fix: `extract_function_body(prompt + gen)` — find the first `def `, keep the function body, truncate at the first top-level line (garbage like `# Driver Code`/`import numpy...`). Judge *that* core only. Verdict: 0/50 → 7/50 on v2 (fibonacci 3/10, binary_search 3/10, two_sum 1/10; quicksort/mergesort stayed 0 — genuinely missing merge/partition helpers, so strictness holds). No false positives (AST-unparseable still fail, no empty-body passes). **Lesson: the judging must be compatible with the model distribution, not just the prompt style.**

## 9. Discussion

### Data quality is a multiplier, not an additive term

The same 435M architecture scores 6/100-equivalent work when fed v1's mismatched pipeline (val 1.97, no generation) and 66/100 when fed the clean pipeline (val 1.27, working implementations). Nothing about the model changed. The v1→v2 delta decomposes into: **a resume path that actually works** (v1's optimizer-references-dead-model bug froze training; its val 1.97 is that bug, not a data-law failure), a matched tokenizer, metadata stripping, data order, and zero repetition — each individually small, jointly decisive. (Note: 353M's still-decent generation with its own loose tokenizer shows the tokenizer mismatch was a supporting factor, not the primary culprit — the frozen-training bug is.)

### Loss predicts, human review decides

val loss ordered every model correctly (1.97 → 1.27 → 1.21-with-asterisk), but within-model claims ("is 16B better than 8B?") were invisible or *inverted* in loss (0.91 best vs 1.21 final) while human review showed unambiguous regression. For small models, loss is a coarse instrument.

### The failed v1 was worth it

Every design decision in this report maps to a specific v1 failure, and the v1 post-mortem (optimizer/object-identity bug — the primary culprit, tokenizer mismatch, cumulative-token arithmetic) caught bugs that would otherwise have silently corrupted v2 as well — the active_lr cooldown bug in v2 was found *because* the v1 audit taught us to diff expected vs actual LR trajectories.

## 11. What I Learned

- **Silent bugs are the expensive ones.** The optimizer-referencing-a-dead-model bug ran for days producing healthy-looking logs and zero learning. Every resume path now gets an object-identity audit.
- **Distribution match is the deepest recurring theme**: tokenizer↔data, fine-tune-data↔eval-task, filter-rule↔corpus. Three different bugs, one principle.
- **Windows is a real training platform, with real footguns**: commit-memory OOM masquerading as VRAM OOM, GBK default encodings, CUDA-graph slowdowns on sm_120. All documented in CHALLENGES.md.
- **Evaluation is a research problem**: we had to build (and then partially dismantle) an execution-based harness before concluding that human-graded generation with fixed prompts is the honest metric at this scale.
- **Write the post-mortem while it hurts.** The v1 failure log is the reason v2 could be trained once, cleanly, in 96 hours.
